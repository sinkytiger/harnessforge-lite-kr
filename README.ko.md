# harnessforge-lite-kr

[English](README.md) · 한국어

긴 공시 문서 더미에서 숫자를 찾아 답하는 리서치 에이전트입니다. 에이전트가 쓰는 하네스(모델 바깥의 프롬프트·도구 안내·스킬·검증 게이트·예산)를 스스로 고쳐 나갑니다. 2026년 10월에 나온 하네스 논문 세 편을 하나로 묶었습니다.

| 논문 | 이 에이전트에서 맡은 역할 |
|---|---|
| **[LongHarness](https://arxiv.org/abs/2610.13075)** | 실행기. 증거 은행(EvidenceBank)에 근거를 쌓고, 근거마다 상태(유효·대체됨·철회됨)를 관리합니다. 결론 상태의 '아직 모르는 것' 목록이 다음 검색을 이끕니다. 인용은 실제로 읽은 구간만 허용합니다. |
| **[Harmony Harness](https://arxiv.org/abs/2610.15150)** | 오프라인 탐색. 정확도와 토큰 비용 두 목표를 MOEA/D(체비쇼프 스칼라화)로 함께 최적화합니다. 편집 연산자는 구성요소(도구·스킬·로직)와 범위(일반·도메인)로 나눠 둡니다. 실행 시점에는 질문에 맞는 부품만 골라 조립합니다. |
| **[Harness²](https://arxiv.org/abs/2610.14224)** | 테스트 시점 개선. 정답지 없이 돌아갑니다. 범용 편집자와 도메인 편집자가 각각 수정안을 내고, 같은 과제에 두 안을 시험 실행한 뒤, 행동 차이로 뒷받침되는 수정만 합칩니다. 배운 점은 경험 라이브러리(EXPERIENCE.md)에 남깁니다. |

> **비공식 구현입니다.** 세 논문의 저자들과 관계가 없습니다. Harness²에는 공식 구현 [google-research/harness2](https://github.com/google-research/harness2)(Apache-2.0)가 있지만 Linux·Node.js·Vertex AI가 필요합니다. 이 저장소는 아이디어만 가져와 처음부터 다시 짠 작은 구현입니다. 핵심 코드는 파이썬 표준 라이브러리만 쓰고 노트북의 무료 로컬 모델로 돌아갑니다. Claude 모델은 선택 사항입니다. 수치는 논문과 **비교할 수 없습니다**.

## 세 논문이 맞물리는 방식

세 논문 모두 모델이 아니라 하네스를 고칩니다. 다만 작동하는 시간 단위가 다릅니다.

```
 오프라인 · 정답 있는 탐색용 세트                     온라인 · 정답 없는 테스트 과제
 초기 H0 ─► Harmony 탐색 (정확도 × 비용) ─► H† ─► 과제마다 Harness² 한 단계 ─► 답
             일반 / 도메인 연산자                    범용·도메인 제안 → 시험 실행 → 합성
                                                      └─► 경험 라이브러리 (EXPERIENCE.md)
 모든 실행은 LongHarness 에피소드:
 search → read(구간 S#) → upsert(근거 E#) → revise → E#로 compute → E#를 인용해 final (게이트 통과 시)
```

세 가지 설계 고리가 있습니다.

1. **범위 구분을 두 진화 방법이 함께 씁니다.** Harmony의 '일반 대 환경 전용 부품'과 Harness²의 '범용 대 도메인 편집자'가 같은 두 폴더(`general/`, `domain/dart/`)를 씁니다. 전이 모드에서는 도메인 부품을 모두 뺍니다.
2. **LongHarness의 명시적 상태 덕분에 정답지 없이도 시험 실행을 비교할 수 있습니다.** "수정이 도움이 됐나?"가 확인 가능한 신호로 바뀝니다. 최종 답이 받아들여졌는지, 어떤 게이트가 거절했는지, 인용한 숫자가 인용 구간에 실제로 있는지, 정정 전 공시나 잠정 공시를 인용했는지, 같은 검색을 되풀이했는지를 봅니다.
3. **검증 게이트가 하네스 부품입니다.** `value_in_source`, `block_repeats`, `correction_check`, `preliminary_check` 같은 게이트는 LongHarness 도구에 붙은 스위치입니다. 어느 루프든 일반 편집으로 켤 수 있습니다.

전체 대응 관계와 논문과 다른 점은 [docs/design.md](docs/design.md)에 정리했습니다.

## 과제: 함정을 심은 합성 DART 공시 코퍼스

LongHarness는 미국 재무부 보고서에 대한 수치 질의(OfficeQA)로 평가합니다. 한국에서 이에 해당하는 것이 DART 공시입니다. 여기서는 정답과 함정을 정확히 알 수 있도록 코퍼스를 **합성**했습니다.

* 가상 기업 16곳의 공시 93건, 약 60만 자입니다. 3개년 사업보고서, 2026년 1분기·반기보고서, `[기재정정]` 사업보고서 6건, 잠정실적 공정공시 7건이 들어 있습니다. 모든 문서에 '연구용 합성 데이터이며 실존 기업과 무관하다'는 문구가 있습니다.
* 질문은 51개입니다. 기업 단위로 나눠 16개는 탐색용, 35개는 테스트용입니다. 테스트 기업은 탐색 중에 한 번도 나오지 않습니다.
* 함정은 LongHarness가 말한 두 실패 유형에 맞췄습니다. *근거 상태 표류*에 해당하는 함정은 정정 전 수치, 잠정 수치, 연결 대신 별도 재무제표, 3개월 대신 누적 열입니다. *끝없는 탐색*에 해당하는 함정은 긴 상용구 속 비슷한 숫자, 거의 같은 문서, 헷갈리는 회사명(한빛전자와 한빛전기)입니다.
* 오라클 정책이 모든 정답 계산을 같은 도구로 재현합니다. CI가 게이트를 모두 켠 상태에서도 51문항 전부를 턴 예산 안에 풀 수 있는지 확인합니다.

**벤치마크 v2 (아직 모델 결과 없음).** 다음 실험용으로 키운 세트입니다. 가상 기업 30곳, 공시 234건, 질문 173개를 탐색·검증·테스트로 나눴습니다. 3분기보고서·감사보고서·잠정실적 정정·상호변경·재작성 수치 같은 문서 유형과 새 질문 유형·함정을 더했고, 공시로는 답할 수 없어 '알 수 없음'이 정답인 질문 15개를 넣었습니다. 실제 DART FY2025 사업보고서 6건에 대한 20문항짜리 소규모 세트는 각자의 DART 키로 로컬에서 만듭니다. 자세한 내용은 [docs/benchmark_v2.md](docs/benchmark_v2.md)에 있습니다. 아래 결과는 모두 v1 기준입니다.

## 무료 로컬 모델로 실행 (Ollama)

[Ollama](https://ollama.com)를 설치하고 구조화 출력을 지원하는 작은 모델을 받습니다. 아래 실험은 `qwen3:4b`를 썼습니다. qwen3는 생각 모드를 자동으로 끕니다. 켜 두면 JSON 행동을 쓰기도 전에 출력 예산을 다 써 버리기 때문입니다.

```bash
python -m harnessforge run --harness seed-longharness --model qwen3:4b --split test --out runs/e1_longharness
```

```bash
python -m harnessforge evolve --harness seed-longharness --model qwen3:4b --n-sub 4 --generations 2 --out runs/e2_harmony
```

```bash
python -m harnessforge refine --harness runs/e2_harmony/best --model qwen3:4b --k 1 --split test --out runs/e3_harness2
```

```bash
bash scripts/run_experiments.sh
```

`--editor-model`로 편집자 모델을 따로 지정할 수 있고, `--scopes general`이면 전이 모드로 돌아갑니다. 에피소드는 (하네스 해시, 질문, 시드, 모델) 단위로 캐시됩니다. Harmony는 체크포인트에서, Harness²는 끝난 과제를 건너뛰고 이어서 돌기 때문에 중간에 멈춰도 다시 시작할 수 있습니다.

## Claude로 실행 (선택)

```bash
pip install -e ".[claude]"
```

API 키는 `ANTHROPIC_API_KEY` 환경변수나 저장소 밖 파일 `~/.harnessforge/anthropic_api_key.txt`에 넣습니다. 파일 경로는 `HARNESSFORGE_KEY_FILE`로 바꿀 수 있습니다. 이미 실행 중인 앱이 새 환경변수를 못 읽을 때 파일 방식이 편합니다. 아래 명령으로 짧은 요청 한 번을 보내 키를 확인합니다.

```bash
python -m harnessforge check-model --model claude-opus-5-5
```

`claude-*` 모델 이름은 `--model`(실행 모델, 기본 effort `low`)과 `--editor-model`(편집자, 기본 effort `medium`)에 모두 쓸 수 있습니다. 요청은 구조화 JSON 출력을 쓰고, 지원하는 모델에서는 서버 측 거절 대체(fallbacks)를 켜서 안전 분류기의 오판 하나로 실험이 멈추지 않게 했습니다.

## 결과

모든 수치는 테스트 35문항(탐색 중 한 번도 나오지 않은 기업 11곳)에서 샘플링 시드 하나로 잰 값입니다. Harmony가 평가한 하네스 전체를 포함한 표는 [reports/results.md](reports/results.md)에 있습니다. 실행 모델은 두 가지를 썼습니다. 하나는 노트북 RTX 2060(6GB)에서 Ollama로 돌린 `qwen3:4b`(무료)이고, 다른 하나는 API로 부른 Claude Haiku 5.5(effort low)입니다. 하네스 편집자는 실행 모델 자신이거나 Claude Opus 5.5(effort medium)입니다. Harness² 논문도 약한 실행 모델에 더 강한 편집자(Claude Opus 4.8)를 붙입니다.

![실행 모델별 정확도](docs/figures/accuracy_by_system.png)

### Claude Haiku 5.5 실행, Claude Opus 5.5 편집자

| 시스템 | 정답 (35문항 중) | 문항당 토큰 | 문항당 비용($) |
|---|---|---|---|
| 검색 후 한 번에 답하기 (상위 6개 청크) | 11 (31.4%) | 4,821 | 0.0007 |
| 도구 + 자유 메모 | 26 (74.3%) | 23,513 | 0.0032 |
| LongHarness 초기 하네스 H0 | 29 (82.9%) | 29,007 | 0.0039 |
| LongHarness 초기 하네스 H0, 두 번째 실행 | 31 (88.6%) | 31,217 | 0.0042 |
| Harmony가 고른 하네스 H† | 29 (82.9%) | 32,232 | 0.0042 |
| H†, 수정 없이 두 번째 실행 (대조) | 29 (82.9%) | 32,110 | 0.0042 |
| H† + Harness² 한 단계 (k=1) | **34 (97.1%)** | 117,603 | 0.1064 |

* **같은 도구에서도 근거를 명시적 상태로 관리하면 자유 메모보다 낫습니다.** LongHarness 초기 하네스는 두 번 실행해 29개와 31개를 맞혔습니다. 자유 메모는 26개, 한 번에 답하기는 11개였습니다. 남은 오답 6개 중 4개는 단위 실수였습니다. 백만원 수치를 100이 아니라 10으로 나누는 식입니다.
* **Harmony는 탐색용 문항에서는 나아졌지만 테스트로는 옮겨 가지 않았습니다.** 탐색용 16문항에서 선택한 하네스는 15개에서 16개로 올랐고 토큰은 8% 줄었습니다. 수정 내용은 도메인 단위 환산 규칙, `unit_declared` 게이트, 항상 켜지는 공시 탐색 스킬이었습니다. 테스트 35문항에서는 초기 하네스와 같은 29개였습니다. 오답의 종류가 바뀌었을 뿐입니다. 단위 실수는 4개에서 1개로 줄었지만 별도·연결 혼동이 2개 새로 생겼습니다. 탐색용 16문항으로는 진짜 개선과 잡음을 구분하기 어렵습니다.
* **Harness²는 정답지 없이 5문항을 새로 맞혔고, 맞던 문항을 틀리게 만들지는 않았습니다.** 합성 단계는 35개 과제 중 16개에서 수정을 채택했고 19개는 그대로 뒀습니다. 고친 사례마다 실행 기록 자체에서 근거를 댔습니다. 천원 수치를 10배 잘못 환산한 경우, 별도 재무제표를 연결로 읽은 경우(2건), 이름이 비슷한 다른 회사(세원바이오와 세원바이오텍)로 넘어간 경우(2건)였습니다. 대신 비용이 단일 실행의 약 25배이고, 거의 전부가 Opus 편집자 호출입니다(35개 과제에 3.26달러).
* **대조 실험으로 '다시 돌려서 나아진 것'이라는 설명을 배제했습니다.** H†를 수정 없이 한 번 더 돌리면 역시 29개였습니다. 6개 오답 중 1개를 고치고 다른 1개를 틀렸습니다. 두 번의 단순 실행 중 문항마다 나은 쪽을 골라도 30개입니다. 초기 하네스도 두 번 실행에서 29개와 31개로 2문항 정도 흔들렸습니다. Harness²가 고친 5문항은 그 범위를 분명히 넘습니다.
* **경험 라이브러리에 교훈 4개가 쌓였습니다.** 예를 들면 "가장 최근 `[기재정정]` 공시를 이미 읽었다면 정정 여부를 다시 확인하지 말고 끝낸다"입니다. 해당 과제에서 같은 답을 39k 대신 21k 토큰으로 냈습니다.

### qwen3:4b 실행 (로컬, 무료)

| 시스템 | 정답 (35문항 중) |
|---|---|
| 검색 후 한 번에 답하기 | 2 (5.7%) |
| 도구 + 자유 메모 | 1 (2.9%) |
| LongHarness 초기 하네스 H0 | 0 (0.0%) |
| Harmony가 고른 하네스 H† (Opus 편집자, 1세대) | 1 (2.9%) |
| H† + Harness² 한 단계 (Opus 편집자) | 5 (14.3%) |

* **4B 모델은 찾기보다 마무리에서 무너집니다.** 대체로 맞는 표까지는 찾아갑니다. 하지만 턴 예산이 끝날 때까지 같은 검색을 되풀이하거나 단위를 틀립니다. 이 모델에서는 기본 하네스들이 모두 0~6%에 머뭅니다.
* **편집자가 중요합니다.** `qwen3:4b`가 스스로 편집자를 맡자 Harmony는 8번 시도하는 동안 탐색용 정확도 0%를 벗어나지 못했습니다. 수정안 3개는 검증에서 거절됐고, 그중 1개는 나중에 고친 편집 스키마 버그 때문이었습니다. Claude Opus 5.5가 편집자를 맡자 1세대(4번 시도) 만에 16문항 중 2개를 맞혔습니다. 이긴 수정은 "`[기재정정]` 공시를 우선하고, 단위 환산은 모두 `compute`로 하라"는 도메인 스킬이었습니다. 테스트 35문항에서 이 하네스는 혼자서 1개를 맞혔고, Harness²를 거치자 5개가 됐습니다. 망가뜨린 문항은 없었습니다. 그래도 35개 중 20개는 끝내 답을 확정하지 못해서, 편집자가 좋아져도 약한 실행 모델을 메우지는 못했습니다.

| 검색 후 한 번에 답하기 | 24 | 0 | 0 | 0 | 5 | 8 | 11 |
| 도구 + 자유 메모 | 9 | 0 | 0 | 1 | 0 | 6 | 2 |
| LongHarness 초기 하네스 H0 | 6 | 0 | 0 | 0 | 0 | 4 | 2 |
| Harmony가 고른 하네스 H† | 6 | 1 | 0 | 2 | 0 | 1 | 2 |
| H† + Harness² 한 단계 | 1 | 1 | 0 | 0 | 0 | 0 | 0 |

한 번에 답하기를 무너뜨린 함정은 잠정 수치와 단위 실수입니다. 도구를 쓰고 근거를 상태로 관리하면 잠정 수치 오답은 사라집니다. 남는 것은 주로 단위 계산, 그리고 재무제표 기준이나 회사를 헷갈리는 실수입니다. 과제별 Harness² 단계가 고친 것이 바로 이 유형입니다.

### 전체 비용

Claude API 정가 기준으로 약 10달러가 들었고, 대부분은 Harness²의 Opus 편집자 호출입니다. qwen3:4b 실행은 무료이고 노트북 GPU로 약 11시간 걸렸습니다.

## 결론과 다음 단계

**이번 실험이 뒷받침하는 것.** 쓸 만한 실행 모델에서는 같은 도구라도 근거를 명시적 상태로 관리하는 쪽이 자유 메모나 한 번에 답하기보다 나았습니다. 정답지 없는 과제별 개선(Harness²)은 테스트 5문항을 고쳤습니다. 단순 재실행으로 바뀌는 폭을 분명히 넘는 차이이고, 대신 비용이 단일 실행의 약 25배였습니다. 정답이 있는 16문항으로 한 오프라인 탐색(Harmony)은 그 16문항에서는 나아졌지만 처음 보는 문항으로는 옮겨 가지 않았습니다. 4B 실행 모델에서는 어떤 하네스도 모델의 한계를 메우지 못했고, 강한 편집자는 조금 도움이 됐을 뿐입니다.

**아직 말할 수 없는 것.** 모든 설정이 한 번의 표본이고, 테스트는 35문항이며, 코퍼스는 합성이고, 실행 모델은 두 개만 써 봤습니다. 관찰을 주장으로 바꾸려면 표본을 늘리고 모델을 더 써 봐야 합니다.

1. **설정마다 3~5번 반복하고 구간을 보고합니다.** Claude 모델은 시드를 고정할 수 없어서, 흔들림을 재려면 반복이 유일한 방법입니다.
2. **두 극단 사이의 실행 모델을 더 써 봅니다.** 8B~30B 공개 모델이나 Claude Sonnet 5.5 같은 모델입니다. 하네스 효과가 어디서부터 나타나는지가 핵심 질문입니다. 4B에서는 없었고 Haiku 5.5에서는 분명했습니다.
3. **Harmony에 더 큰 탐색용 세트와 더 많은 세대를 줍니다.** 그래야 탐색용 세트의 개선을 잡음과 구분하고, 처음 보는 문항으로 옮겨 가는지 확인할 수 있습니다.
4. **Harness²를 k > 1로 돌리고,** 논문처럼 경험 라이브러리를 뺀 비교도 합니다.
5. **Harness² 비용을 줄입니다.** 편집자 호출을 줄이고, 쉬운 과제에는 싼 편집자를 쓰고, 라이브러리를 더 재사용합니다.
6. **합성 데이터에서 실제 DART 공시로 옮깁니다.** 질문 정답은 DART 재무 API로 검증합니다. 이번 단계용 질문 세트([v2와 소규모 실제 세트](docs/benchmark_v2.md))는 만들어 두었고, 아직 모델은 돌리지 않았습니다.

## 진화가 바꿀 수 있는 것과 고정된 것

하네스는 작은 파일 묶음입니다. **도구**는 `tool_guidance.md`와 `search_k`·`snippet_chars`·`read_chars` 세 손잡이입니다. **스킬**은 키워드로 불려 나오는 짧은 지침 파일입니다. **로직**은 `system.md`·`domain.md`, 턴 수·이력 창·스킬 수·생각 길이 손잡이, 게이트 스위치입니다. 모든 편집은 JSON 연산이고, 적용 전에 검증합니다. 허용된 구성요소와 범위인지, 값이 범위 안인지, 크기 제한을 넘지 않는지 봅니다. 코퍼스 회사명이나 큰 특정 숫자가 들어가면 유출 방지 규칙에 걸려 거절됩니다.

코퍼스, 검색 색인, 도구 동작, 채점, 정답은 바꿀 수 없는 평가 인터페이스입니다. Harness² 루프는 정답을 한 번도 보지 않습니다. Harmony는 탐색용 세트에서만 정답과 함정 라벨을 봅니다. Harmony 논문이 진화용 세트에서 실패한 테스트를 보는 것과 같은 방식입니다.

## 한계

* 작은 합성 벤치마크입니다(테스트 35문항, 탐색용 16문항). 절대 수치로 최신 대형 모델을 말할 수는 없고, 상대 비교와 실패 분석이 핵심입니다.
* 설정마다 샘플링 시드 하나입니다. Claude 모델은 시드를 고정할 수 없어서 Claude 행은 각각 한 번의 표본입니다. 한두 문항 차이는 잡음 범위입니다.
* 진화 예산이 작고 조건마다 다릅니다. Haiku는 Harmony 2세대(수정안 8개), qwen3:4b + Opus 편집자는 시간 때문에 1세대(4개)만 돌렸습니다. Harness²는 모두 k=1입니다.
* 이력 압축 방식이 LongHarness와 다릅니다. 논문은 전체 이력을 그대로 두지만 8k 토큰 로컬 모델에서는 불가능합니다.
* 실험 중 생긴 일 두 가지를 숨기지 않고 남깁니다. 하나는 편집자가 필수 필드를 빠뜨려도 통과하던 편집 스키마 버그입니다. Claude 편집자 Harmony 두 개는 고친 뒤 다시 돌렸고, qwen 편집자 실험에는 그 버그로 거절된 수정안 1개가 남아 있습니다. 다른 하나는 Haiku Harmony 도중 네트워크가 끊긴 일입니다. 이 실행은 체크포인트에서 이어서 돌렸습니다.
* 개발 중 테스트 첫 5문항으로 도구 버그를 찾았습니다. 생각 모드, 표 머리글이 잘리는 읽기 창, 엉뚱한 필드에 들어간 문서 ID가 그것입니다. 초기 프롬프트를 테스트 문항에 맞춰 조정하지는 않았습니다.
